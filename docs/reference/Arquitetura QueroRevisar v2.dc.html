Por que não Vercel e Railway

O plano grátis da Vercel é só para uso pessoal e não comercial, e o QueroRevisar tem Premium e anúncio. O plano grátis do Railway dá US$ 1 de crédito por mês, pouco para uma JVM ligada o mês todo, e cobra por memória e CPU ligadas, não por requisição. No Cloud Run, com a cobrança por requisição, cada chamada evitada pelo cache é economia direta.

A regra de vencimento existe em duas linguagens

O web app calcula "vence em 1.200 km" offline (TypeScript) e a API dispara o alerta (Kotlin). Os dois rodam a mesma bateria de casos em fixtures/. Se um lado mudar e o outro não, o CI falha.

PWA no iOS e no Android

Android
Quase igual a um app
O Chrome oferece "Instalar app" sozinho
Ícone, tela cheia, push, offline
Sincronização em segundo plano funciona
iOS
Funciona, com três limites
Instalação manual: Safari → Compartilhar → Adicionar à Tela de Início
Push só depois de instalado e autorizado (iOS 16.4+)
Sem sincronização em segundo plano. A fila sai quando o app abre
Instalar faz parte do onboarding

Sem instalar, o iPhone não recebe alerta, e o alerta é o produto. Depois do primeiro veículo cadastrado, o app detecta o iOS e mostra o passo a passo de instalação com imagens. Ao abrir já instalado, pede permissão de notificação e chama navigator.storage.persist() para o sistema não apagar os dados locais.

Para entrar nas lojas depois, o mesmo web app pode ser empacotado com Capacitor. A decisão de hoje não fecha essa porta.

Menos requisições

Com o Cloud Run cobrando por requisição e por tempo de processamento, aqui está o que mantém a conta em zero. Os dados do usuário mudam pouco e quase sempre por ação dele mesmo, o que permite cache agressivo.

Catálogo como arquivo estático
Os 175 itens e os planos de fabricante viram um JSON versionado na Cloudflare (catalogo.v12.json). O app baixa uma vez e guarda. Zero chamadas à API.
Uma chamada para abrir o app
GET /v1/sync?desde=… devolve só o que mudou desde a última abertura: veículos, registros, plano, versão do catálogo. Na maioria das vezes volta vazio.
Cache persistido no cliente
TanStack Query com persistQueryClient em IndexedDB e staleTime longo. Sem refetch ao focar a janela. Depois de salvar, atualização otimista e invalidação só da chave afetada.
ETag e 304
Respostas de leitura levam ETag. Se nada mudou, a API responde 304 sem corpo, em poucos milissegundos.
Escritas em lote
A fila offline manda várias alterações num único POST /v1/sync.
Push em vez de polling
O app nunca pergunta "tem alerta?". O job do servidor calcula e avisa por Web Push.
Respostas rápidas
O Cloud Run cobra o tempo de cada requisição. Índices certos no Postgres, Caffeine para catálogo e flags, nada de chamada externa no caminho de leitura.

Login

A pessoa entra como usuário anônimo do Supabase e já usa o app, como pede a Estratégia v2. Para guardar na nuvem ou assinar, vincula um login à mesma conta, sem perder nada.

No lançamento: e-mail e senha, código ou link por e-mail, Google. Depois: SMS (pago por envio) e Apple (exige a conta de desenvolvedor de US$ 99/ano).

Offline e sincronização

App abre sem rede
O service worker guarda o app e o catálogo. Os dados do usuário ficam em IndexedDB.
IDs criados no aparelho e fila de saída
Todo registro nasce com UUID v7 gerado no cliente, que serve de ID e de chave de idempotência. Sem rede, a alteração entra na fila e a tela já mostra o resultado. Com rede, a fila sai em lote.
Conflito
Registros de troca são quase só inclusão. Quando há conflito, vale a última gravação por registro, com o horário do servidor. Exclusão é marcada (soft delete) para propagar entre aparelhos.
O que funciona sem rede
Ver painel e histórico, registrar troca, atualizar km. Login, assinatura e busca de oficina pedem rede.

Jobs e notificações

Agendamento
Cloud Scheduler chama rotas internas da API, autenticadas
A API não fica ligada esperando o horário. A camada grátis cobre alguns jobs por conta.
Job diário, 6h
Atualiza a km estimada, recalcula itens perto do vencimento, grava os alertas a enviar. Também mantém o Supabase ativo, o que evita a pausa por inatividade do plano grátis
Envio, 9h
Um resumo por veículo, não um push por item
Push
Web Push com chaves VAPID, enviado direto pela API. Sem serviço pago no meio
E-mail
Resend para alertas e para os e-mails de login (SMTP configurado no Supabase, porque o envio padrão do Supabase tem limite muito baixo)
E-mail é o plano B de quem não instalou o PWA no iPhone.

Cobrança do Premium

Asaas: assinatura recorrente com cartão, Pix e boleto, webhooks e sandbox. Sem mensalidade, só taxa por cobrança. Mercado Pago como alternativa.

Sem loja, não há comissão de Apple ou Google e o checkout pode ficar dentro do app. O status do plano é atualizado só por webhook. O app lê o plano no /v1/sync e nunca decide sozinho se a pessoa é Premium.

CI/CD

Pull request
Lint, typecheck, testes do que mudou (Turborepo), testes da API na JVM com Postgres real (Testcontainers), checagem do cliente gerado contra o OpenAPI. Preview da web na Cloudflare.
Merge na main
Build da imagem nativa, migração Flyway no banco de dev, deploy no "api-dev" e na web de dev.
Tag de versão
Aprovação manual, migração em prod, deploy da mesma imagem já testada em dev. O Cloud Run troca as instâncias sem queda e permite voltar para a versão anterior em um clique.

O build nativo leva vários minutos. Ele roda só no merge e na tag, não em todo PR, para caber nos minutos grátis do GitHub Actions.

Backup e recuperação

O Supabase free não tem backup. Por isso o backup próprio é obrigatório desde o primeiro usuário.

Diário
pg_dump toda noite via GitHub Actions, criptografado, no Cloudflare R2. Guarda 30 dias
Teste
Uma vez por mês, restaurar num banco vazio e rodar a suíte. Backup que nunca foi restaurado não conta
Meta
Perder no máximo 24h de dados no servidor e voltar em até 4h. O aparelho ainda guarda a cópia local
